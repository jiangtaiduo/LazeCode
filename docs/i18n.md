# Internationalization (i18n)

[English](i18n.md) | [Simplified Chinese](i18n.zh-CN.md)

The single source of truth for UI text is `src/services/i18n/`. Rust keeps two
unavoidable mirrors: the native menu labels and the error-code protocol. An
automated check guards each mirror against drift.

## Files

| File | Responsibility |
| :--- | :--- |
| `types.ts` | The `LocaleDict` contract. **The only authority for keys**; add a new key here first. |
| `en.ts` | English, the base language. Every key must be present. |
| `zh-CN.ts` | Simplified Chinese. Uses `satisfies LocaleDict` to stay aligned with English. |
| `index.ts` | Runtime: `t()` lookup, current language, `setLanguage`, `initLanguage`, subscriptions. |
| `languageCore.ts` | `DEFAULT_LANGUAGE` and `normalizeLanguage`, shared by settings and tests. |
| `errors.ts` | Backend error codes to text in the current language. |

## Usage

```ts
import { t } from '../services/i18n';

// Static string
t().common.close;

// String with parameters (dictionary values are callable functions)
t().status.saveFailed(msg);
t().git.branchCreatedFrom(from, name);
```

**Call `t()` at render time; do not cache the result in a module-level
constant.** The dictionary is module-level state, not React state. Language
changes trigger a re-render through the App subscription; a value stored in a
`const` stays frozen in the language that was active when it was evaluated.

## Adding or changing text

1. Add the key to `LocaleDict` in `types.ts` (choose an existing section or
   create one).
2. Add the value to both `en.ts` and `zh-CN.ts`. `tsc` enforces that the two key
   sets match.
3. Update the call site to use `t()`.

Sections are lowercase (`git`, `status`, `welcome`, …); keys are camelCase.
English values need correct plural forms (`file` / `files`); Chinese does not.

## Adding a language

1. Create `src/services/i18n/<lang>.ts` with
   `export const xx: LocaleDict = { ... }`.
2. Add the language to the `Language` union in `types.ts` and register it in
   `LOCALES` in `index.ts`; add its display name to `LANGUAGE_LABELS`.
3. Add the tag to `normalizeLanguage` in `languageCore.ts`.
4. Add an `<option>` to the language dropdown in `SettingsDialog`.

Existing call sites do not need changes. Native menu labels are currently
defined only for English and Simplified Chinese; a third UI language needs a
Rust `MenuLabels` table too, or the menu will fall back to English.

## Language setting

- Persisted in `AppSettings.language` (localStorage key `lazecode.settings`).
- Defaults to `en`; there is **no system-language detection**.
- `normalizeLanguage` maps `zh`, `zh_CN`, `zhCN` and `ZH` to `zh-CN`; all other
  unknown values fall back to `en`.
- The Rust side must implement the same mapping, otherwise the window can show
  one language while the native menu shows another.

## Native menu

The native menu is built in `setup()`, before any frontend code runs, so it
cannot read the frontend dictionary. `src-tauri/src/menu.rs` therefore keeps a
`MenuLabels` table for English and Simplified Chinese.

The two copies can drift, so `verify:menu` compares them:

```bash
npm run verify:menu
```

It checks 41 labels per language and exits non-zero on any mismatch. It is part
of `npm run check`.

The menu language is also persisted in `{app_config_dir}/language`, because
Rust cannot read localStorage. The `set_app_menu_language` command updates that
file when the user switches languages, so the first frame after the next launch
uses the correct menu language.

## Backend error protocol

Backend errors used to contain hard-coded Chinese text. The frontend then
wrapped them in an English template, producing mixed-language messages. The
backend now returns a structured string:

```text
ERR:<code>|<detail>
```

- `<code>` is a stable ASCII identifier in snake_case (for example
  `path_not_found`).
- `<detail>` is **untranslated context** (a path, a name, the original system
  error) inserted verbatim.

`describeBackendError()` in the frontend maps the code to the current
language. The protocol parser and its tests are in
`src-tauri/src/error_proto.rs` (5 unit tests).

Fallback order:

1. Code exists in the dictionary: use the current language template.
2. Code is missing: display the entire original string, including the `ERR:`
   prefix. This is deliberate: a missing key is a bug that should be visible.
3. The string is not structured: display it verbatim.

Backend call sites use `crate::error_proto::coded("code", detail)`. In
`App.tsx`, route errors through `errText(err)` instead of hand-writing a catch
block; missing a call site silently reintroduces mixed-language messages.

## Checks

```bash
npm run check           # verify:wire + verify:menu + verify:i18n + tsc
npm run verify:menu     # native menu and frontend dictionary
npm run verify:error-codes
npx tsc --noEmit        # key sets in en / zh-CN
cd src-tauri && cargo test
```

`verify:error-codes` currently reports 85 backend codes, and both dictionaries
contain all 85. It also warns about dictionary keys that no backend code
produces.

## Keys must stay ASCII

Keys in `en.ts` and `zh-CN.ts` are always ASCII; only values are translated.
If a key is renamed to a non-ASCII identifier, `t().search.tabFiles` becomes
`undefined` in the other language, and changing both dictionaries together will
still pass `tsc`. `verify:i18n` walks both objects, rejects non-ASCII keys and
requires the same structure; it is part of `npm run check`.

## Pitfalls

- **Module-level constants freeze the language.** Values that call `t()` must be
  produced by a function at render time, not by a `const` evaluated at import
  time.
- **Code and key casing differ.** Backend codes are snake_case
  (`path_not_found`); dictionary keys are camelCase (`pathNotFound`).
  `describeBackendError` performs the conversion.
- **Normalization must match on both sides.** A Rust rule that accepts only
  `zh-` and a frontend rule that accepts any `zh` prefix produce a split
  language state for inputs such as `zhCN`.
