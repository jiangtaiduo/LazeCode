# 界面多语言（i18n）

[英文](i18n.md) | 简体中文

界面文案的唯一真相在 `src/services/i18n/`。Rust 侧只保留两份不可回避的镜像：
原生菜单文案和错误码协议。两份镜像各有一个自动校验，防止漂移。

## 文件职责

| 文件 | 职责 |
| :--- | :--- |
| `types.ts` | `LocaleDict` 类型契约。**所有 key 的唯一权威**；新增 key 先改这里。 |
| `en.ts` | 英文，基准语言。所有 key 必须齐全。 |
| `zh-CN.ts` | 简体中文。用 `satisfies LocaleDict` 对齐英文。 |
| `index.ts` | 运行时：`t()` 查表、当前语言、`setLanguage`、`initLanguage` 和订阅。 |
| `languageCore.ts` | `DEFAULT_LANGUAGE` 与 `normalizeLanguage`，由设置层和测试共用。 |
| `errors.ts` | 后端错误码到当前语言文案的映射。 |

## 使用

```ts
import { t } from '../services/i18n';

// 静态串
t().common.close;

// 带参串（字典值是可调用函数）
t().status.saveFailed(msg);
t().git.branchCreatedFrom(from, name);
```

**渲染时调用 `t()`，不要把结果缓存到模块级常量。** 字典是模块级状态，不是
React 状态。语言切换通过 App 的订阅触发重渲染；一旦把结果存进 `const`，这个值
就会冻结在求值时的语言上。

## 新增或修改文案

1. 在 `types.ts` 的 `LocaleDict` 中加入 key（选合适的分组，没有就新建）。
2. 在 `en.ts` 和 `zh-CN.ts` 中同时加入值。`tsc` 会强制两边的 key 集合一致。
3. 把调用点改成 `t()`。

分组名用小写（`git`、`status`、`welcome` 等），key 用驼峰命名。英文要注意
单复数（`file` / `files`），中文不需要。

## 新增语言

1. 新建 `src/services/i18n/<lang>.ts`，内容为
   `export const xx: LocaleDict = { ... }`。
2. 在 `types.ts` 的 `Language` 联合类型中加入该语言，在 `index.ts` 的
   `LOCALES` 中登记，并在 `LANGUAGE_LABELS` 中补充显示名。
3. 在 `languageCore.ts` 的 `normalizeLanguage` 中加入对应标签。
4. 在 `SettingsDialog` 的语言下拉中加入一个 `<option>`。

已有调用点不需要修改。原生菜单目前只有英文和简体中文两套 `MenuLabels`；如果要
加入第三种界面语言，还需要在 Rust 侧补充菜单表，否则菜单会回落到英文。

## 语言设置

- 持久化在 `AppSettings.language`（localStorage 键为 `lazecode.settings`）。
- 默认 `en`，**不做系统语言探测**。
- `normalizeLanguage` 会把 `zh`、`zh_CN`、`zhCN` 和 `ZH` 归一为 `zh-CN`；
  其余未知值回落到 `en`。
- Rust 侧必须实现同样的映射，否则会出现「界面一种语言、原生菜单另一种语言」。

## 原生菜单

原生菜单在 `setup()` 中构造，早于前端任何代码执行，因此读不到前端字典。
`src-tauri/src/menu.rs` 因此保留了一份英文和简体中文的 `MenuLabels` 表。

两份文案可能漂移，所以有 `verify:menu` 校验：

```bash
npm run verify:menu
```

它会逐项比对每种语言的 41 条文案，不一致时以非零状态退出，并已挂进
`npm run check`。

菜单语言还会单独持久化在 `{app_config_dir}/language`，因为 Rust 读不到
localStorage。用户切换语言时，`set_app_menu_language` 命令会同步写入该文件，
保证下次启动首屏使用正确的菜单语言。

## 后端错误码协议

后端错误原先包含硬编码的中文。前端再把它套进英文模板，就会出现中英混排。现在
后端返回结构化串：

```text
ERR:<code>|<detail>
```

- `<code>` 是稳定的 ASCII 标识，采用蛇形命名（例如 `path_not_found`）。
- `<detail>` 是**未经翻译的上下文**（路径、名称、系统错误原文），前端原样插入。

前端 `describeBackendError()` 负责把错误码映射成当前语言。协议解析和测试在
`src-tauri/src/error_proto.rs`（5 个单元测试）。

兜底顺序：

1. 错误码在字典里：使用当前语言模板。
2. 错误码不在字典里：原样显示整条字符串，包括 `ERR:` 前缀。这是刻意的：漏 key
   是应当被发现的缺陷。
3. 不是结构化串：原样显示。

后端调用点使用 `crate::error_proto::coded("code", detail)`。在 `App.tsx` 中统一
走 `errText(err)`，不要在错误处理分支里各写一遍；漏掉的错误处理分支会悄悄退回中英混排。

## 校验

```bash
npm run check           # verify:wire + verify:menu + verify:i18n + tsc
npm run verify:menu     # 原生菜单与前端字典
npm run verify:error-codes
npx tsc --noEmit        # en / zh-CN 的 key 集合
cd src-tauri && cargo test
```

`verify:error-codes` 当前报告 85 个后端错误码，两本字典都覆盖了这 85 个；它还会
提示字典中存在、但后端不再产生的 key。

## key 必须是 ASCII

`en.ts` 和 `zh-CN.ts` 中的 key 一律使用 ASCII，只翻译值。如果把 key 也翻译了
（例如把 key 翻译成中文标识），`t().search.tabFiles` 在另一种语言下就会变成
`undefined`；即使两边一起改错，`tsc` 也照样通过。`verify:i18n` 会递归比对两本
字典的结构并拒绝非 ASCII key，已挂在 `npm run check` 中。

## 容易踩的坑

- **模块级常量会冻结语言。** 任何调用 `t()` 的值都必须由函数在渲染时产生，
  不能在模块加载时用 `const` 求值。
- **错误码与字典 key 的命名不同。** 后端错误码是蛇形（`path_not_found`），
  字典 key 是驼峰（`pathNotFound`）。`describeBackendError` 负责转换。
- **两侧归一化规则必须一致。** Rust 只接受 `zh-` 前缀、前端接受任意 `zh`
  前缀时，`zhCN` 这类输入会让界面和菜单停在不同语言。
